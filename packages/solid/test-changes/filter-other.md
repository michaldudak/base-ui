# Test changes: filter-other

- `filter-root/MenuFilterRoot.react17.test.tsx`, "omits partial ids during SSR and wires relationships after hydration": skipped (`it.skip`, `// Solid port: React 17 only`). It tests React's id fallback when `React.useId` is missing (the `@base-ui/utils/safeReact` mock), which has no Solid counterpart, and the Solid `createRenderer` has no `renderToString`/`hydrate`. Body kept as a block comment translated to Solid syntax; the `safeReact` mock is dropped.
- `filter-root/MenuFilterRoot.react17.test.tsx`, "registers a submenu trigger after fallback ids resolve": skipped for the same reason. The keyboard flow it drives (enter a filterable submenu, `aria-controls` on its trigger) is generic, but the title and the `base-ui-\d+` id assertion are about the React 17 fallback ids resolving after hydration. Body kept as a block comment.
- `filter-root/MenuFilterRoot.webkit.test.tsx`, `Test` helper (used by "keeps selection state when a focused input is replaced" and "keeps selection in sync when a focused input is replaced without autofocus"): `key={props.inputKey}` on `Menu.Input` became `<For each={[props.inputKey]}>`, which re-creates the input when the key changes, as React remounts it. `{props.showInput !== false && ...}` became `<Show>`.
- `filter-root/MenuFilterRoot.webkit.test.tsx`, "keeps selection state for an auto-focused input in Strict Mode": `React.StrictMode` became a stand-in component that renders its children (Solid has no StrictMode), so the test only checks the auto-focused input path once.
- `filter-root/MenuFilterRoot.webkit.test.tsx`, "does not restore selection after a focused input unmounts and the menu reopens on hover": `React.useEffect(..., [props.close])` became `useEffect(() => [props.close], ...)` from `#utils/useEffect`; the `open` signal is created with `{ ownedWrite: true }` because the effect writes it.
- `filter-root/MenuFilterParts.test.tsx`, "throws when <Menu.%s> is rendered without a filter provider": the `it.each` rows hold functions (`() => <Menu.Input />`) instead of elements, since creating the element at definition time would run the component outside `render`.
- `filter-root/useMenuFilterItem.test.tsx`, "matches an item whose children are an array while it is filtered out": `fireEvent.change(input, ...)` became `fireEvent.input(input, ...)`. React's `onChange` on a text input reacts to the change event fired by Testing Library; the Solid input listens to the native `input` event (guide: `onChange` → `onInput`). (Note: `MenuFilterRoot.test.tsx`, another group, kept `fireEvent.change`.)
- `filter-root/useMenuFilterItem.test.tsx`, "matches the updated text of an item rendered through its render element" and "matches a render element whose text changed while the item was filtered out": `render={<div>{props.name}</div>}` became `render={(elementProps) => <div {...elementProps}>{props.name}</div>}` (render-function form; the element's own children are kept, as `cloneElement` keeps them).
- `filter-root/MenuFilterRoot.scoping.test.tsx`, "announces a dialog from a detached trigger attached to a filterable root" and "does not warn for a filterable menu with an input and a detached trigger": `useRefWithInit(() => Menu.createHandle()).current` became `Menu.createHandle()`, since the component body runs once.
- `filter-submenu-root/MenuFilterSubmenuRoot.test.tsx`, "keeps externally filtered items while the submenu animates out": the per-render `results` became a `createMemo`, and `results.map(...)` a `<For>`.
- `filter-submenu-root/MenuFilterSubmenuRoot.test.tsx`, "keeps focus in the submenu input when the pointer crosses the trigger again": `ReactDOM.flushSync(() => fireEvent.mouseMove(trigger))` became `fireEvent.mouseMove(trigger)`, since `fireEvent` applies pending Solid updates itself (guide section 8).
- `filter-submenu-root/MenuFilterSubmenuRoot.test.tsx`, `Submenu` helper (used by "moves a horizontal parent on when a vertical submenu closes on its main-axis key ...", "does not wrap a filterable parent when closing from its first item ..." and "moves a filterable parent on when a submenu portaled into a shadow root closes"): the `submenu` element became a function called where it is placed, and the provider choice moved into JSX (`<Show when={props.filterable} fallback={submenu()}>`), so the submenu is created inside `Menu.FilterProvider` when there is one (Solid resolves context at creation).
- `filter-submenu-root/MenuFilterSubmenuRoot.test.tsx`, "moves a horizontal parent on when a vertical submenu closes on its main-axis key (...)": the `menu` element built in the test body became a function, called inside `render(() => ...)`, for the same reason.
- `filter-submenu-root/MenuFilterSubmenuRoot.pointerFocus.test.tsx`, `Test` helper (all tests in the file): `const Provider = props.filteredParent ? Menu.FilterProvider : React.Fragment` became `<Dynamic component={props.filteredParent ? Menu.FilterProvider : Fragment}>` with a pass-through `Fragment` stand-in (Solid has no Fragment component and the body runs once).
